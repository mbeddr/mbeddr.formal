## A2 — why neither editor test can be expressed

Both conclusions come from the generated editor code, not from assumption.

**(a) typing a chain into a specialization/subsetting far-end cell — impossible.**
`KerMLFeatureTyping_EditorBuilder_a.createAlternation_0()` chooses the cell via
`KerMLSpecialization.isGeneralChainShown(...)`, which is
`general == null && ownedRelatedElement.isNotEmpty() && !isSpecificChainShown()`. With an **empty** far end the
alternation therefore renders `createRefCell_0()`, and that builder's only `setCellId` calls are
`Collection_…`, `Constant_…`, `refNodeList_ownedRelatedElement` and `ReferencePresentation_…` — the `RefCell`
alternative has **no cell id at all**. An id-less cell cannot be addressed by an `AnonymousCellAnnotation`, so
the harness can neither place the caret in it nor type into it. Same limitation `_390`–`_393` recorded ("the
target reference cell has no addressable cell id"). The addressable `refNodeList_ownedRelatedElement`
alternative only exists once a chain is already present, so it can never be the entry point.
Fallback: `testSubsettingEndShowsChainText` asserts the state a user ends up with, and is mutation-checked.

**(b) typing `chains a . b` into `KerMLFeature_Editor`'s chaining list — impossible.**
`createCustomFactory_56()` wraps the whole `chains` cell in
`showWrapped() = AttributeOperations.getChildNodesAndAttributes(myNode, ownedFeatureChaining).isNotEmpty()`
and returns an **empty vertical collection when that is false**. So a feature with **zero** chainings renders
no `chains` keyword and no `refNodeList_ownedFeatureChaining1` — there is nothing to type into. Once chainings
exist, the keyword is an optional keyword `CellModel_Constant` (`Constant_9bg1ue_a0u0a0`), the very cell kind
`_390`–`_393` documented as undrivable (keyword typed from the name cell is absorbed into the name;
`Complete_Action` + ENTER does not create the relationship; backspace does not delete it). The only fixture that
would render the list already has one chaining — and a one-step chain is now an error by design, so that
fixture is invalid by construction.
Fallback: the resulting state is already covered — `_270`'s `testChainingFeaturesAreTheChainedFeatures`
(two-step chain's steps are the chained features) plus the new `chainEndFeature`/`chainText` tests.

**Consequence worth a decision:** because `showWrapped()` gates the entire `chains` cell, a user cannot reach
the chain from an empty feature either; the first chain must come from a substitute/transform action or
completion. That is a product gap independent of testability — observation 1.

## Step B — read-only slot survey (no model change made)

Order step 3 asks for the concept and slot names before building each relationship, so I checked the three
far-end slots. Nothing was modified.

| relationship | concept | chain slot | own / inverted side | standalone form |
|---|---|---|---|---|
| `inverse of` | `KerMLFeatureInverting` (`< KerMLRelationship`) | `ownedRelatedElement [0..n]` (free) + optional `invertingFeature` reference | **none exists** | **none exists** |
| `::>` / `references` | `KerMLReferenceSubsetting` (`< KerMLSubsetting`) | `ownedRelatedElement [0..n]` | `general` / `specific`, both `0..1` | via `specific` |
| `=>` / `crosses` | `KerMLCrossSubsetting` (`< KerMLSubsetting`) | `ownedRelatedElement [0..n]` | `general` / `specific`, both `0..1` | via `specific` |

Two useful consequences:

- **`::>` and `=>` inherit exactly the shape I exercised with `:>`** in `_430` (`KerMLSubsetting` with
  `general`/`specific` + an owned chain in `ownedRelatedElement`), so the 2b-1 pattern transfers unchanged and
  `effectiveEnd`/`generalText`/`isGeneralChainShown` should already work for them through the inherited
  `KerMLSpecialization` behavior. `KerMLFeatureInverting` is **not** a `KerMLSpecialization`, so it gets none of
  that for free — it needs its own accessors.
- **There is no standalone `inverse` form in our language.** `KerMLFeatureInverting` has no `specific`
  reference, and its generated behavior descriptor declares only `getScope` — no `isStandalone`, no
  `specificType`, no text accessors — unlike `KerMLSpecialization`. So the order's "as the inverted (own) side
  … if our language has one" resolves to: it does not, and adding it would need a structure change (a
  `specific`-style slot), which the order says must be a QUESTION rather than an invention. **QUESTION for you:
  should 009 introduce a standalone `inverse` form (structure change), or is the far-end-only support enough
  for now?** I recommend far-end only for 009, matching what the importer currently parses.

## Unsolicited observations

1. **A user cannot create the first chain from the editor.** `KerMLFeature_Editor.createCustomFactory_56()`
   renders the `chains` keyword and its list only when `ownedFeatureChaining` is non-empty, and the
   specialization/subsetting far end is a plain `RefCell` until an owned chain exists. So on a fresh
   `feature x` no cell offers a chain; the first chain must come from a substitute menu, completion, or
   transform. **Suggested action:** decide whether that is intended; if not, render the `chains` cell on an
   empty feature (e.g. as an optional keyword cell). That would also make A2-(b) expressible later. Product
   question, not a test question.
2. **The 008 rule is now demonstrated on a relationship-owned chain** (the one-step `xOne` case), so its
   applicability there is no longer an inference. Worth keeping `xOne` as the canonical negative fixture.
3. **`generalText()` is the cheapest guard for the editor alternation.** `_430`'s
   `testSubsettingEndShowsChainText` fails if `isGeneralChainShown()`/`effectiveEnd()` regress without needing
   an editor test. Extend the same trick to `specificText()` when 2b-2 adds the specific-side chain — the
   `isSpecificChainShown()` branch is still untested.
4. **Fixture-authoring note for Step B:** a chain needs each intermediate step typed (`a : T`, `T::b : U`)
   before the next step resolves, and name-based references in a blueprint resolve within one classifier but
   not across classifiers — there I had to set `chainingFeature` by node reference afterwards. Expect that for
   every 2b-2 relationship fixture.
5. **Operational:** for long iterations, run the full suite and the force-save earlier rather than only at the
   end; this iteration lost one closing pass to an MPS restart.
